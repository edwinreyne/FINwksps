| D-16 | 视觉采用低饱和蓝白桌面工作台 | 参照用户附件，以 1920×1080 PC 为主演示分辨率，第一版不考虑移动端体验 |

## 3. 设计假设

| ID | 假设 | 当前默认值 | 若错误的影响 |
| --- | --- | --- | --- |
| A-01 | 演示会话状态的持久化深度 | 默认在浏览器本地保存，支持重置演示；不建设生产后端 | 若需跨设备或多人协作，需要增加服务端状态层 |
| A-02 | 一个统一 Case 状态机可覆盖三场景 | 主场景完整展示；另两场景通过代表页面验证复用 | 若流程差异更大，需子流程/编排模型 |
| A-03 | 审批采用 RBAC + 事项/属性策略 | 角色、范围、金额、风险及 SoD 组合 | 影响权限模型和演示账号 |
| A-04 | 价值验证由财务数值验证、业务可持续性确认 | 双责任确认 | 影响关闭条件和责任分配 |
| A-05 | 知识发布必须人审 | 关闭 Case 后先生成草稿 | 影响自动沉淀速度但降低错误传播 |
| A-06 | 原型用虚构 FY27 演示周期和人民币主币种 | 可切单位/币种，仅展示换算 | 若需多账簿/多币种，会扩展语义模型 |
| A-07 | 审批阈值使用演示配置而非公司现行政策 | 清楚标记 DEMO，至少三级 | 不妨碍体验，但不可用于真实授权判断 |
| A-08 | 模拟 Agent 采用确定性场景脚本 | 保留 Run、置信度、审批、停止、失败和接管体验 | 若需更开放的交互，需要扩展模拟规则但仍不调用真实模型 |

## 4. 关键取舍

### 4.1 事项中心 vs 页面中心

选择事项中心：业务域页面负责发现和组合分析，最终决策/授权/行动回到 Case。代价是 Case 信息较多，因此用摘要、页签和质量门降低认知负担。

### 4.2 统一机制 vs 三套专用流程

选择统一领域对象和控制机制、类型化模板与质量门。这样可跨流程查询、审计和复用；不强求三类业务字段完全相同。

### 4.3 Agent 自由度 vs 可控性

近期优先可控性：模型与工具隔离、执行需细粒度授权、低置信度转人、失败熔断。牺牲部分自动化速度，以满足财务责任和审计要求。

### 4.4 实时视图 vs 决策可复现

业务页面可展示最新值，但提交审批时固定 Evidence/Option 快照。代价是需要版本管理；收益是能还原“当时基于什么作决策”。

### 4.5 价值聚合 vs 防止重复计算

允许 Action 关联多个 Cases，但指定主 Case 负责价值归属；组合看板按唯一 Action/Verification 聚合。

## 6. 未采用或暂缓方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 以十个模块为独立门户菜单 | 不采用 | 破坏事项闭环、上下文与审计连续性 |
| 每个场景建设独立审批/任务对象 | 不采用 | 重复能力，跨场景组合和控制困难 |
| 原型直连真实数据以提高真实感 | 不采用 | 与本轮安全边界冲突，且会提前引入集成风险 |
| Agent 自动批准或自行扩展权限 | 不采用 | 与人类最终授权和职责分离冲突 |
| 保存模型完整思维链作为解释 | 不采用 | 以输入引用、方法、假设、结构化理由和限制满足可解释/审计 |
| 本轮确定生产技术栈 | 暂缓 | 尚未确认部署、安全、容量与企业标准，原型设计不应锁死技术 |
